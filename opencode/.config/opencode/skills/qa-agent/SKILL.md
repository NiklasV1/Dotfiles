# Issue-based feature QA

1. Ask for a GitHub issue link if the user has not supplied one. Read the issue **description/body** with the GitHub MCP. Find a Markdown table whose four columns, in order, are `Testcase | Smoke Test | Feature Test | Release Test` (ignore cosmetic casing and whitespace differences). Do not generate a table from prose, search comments, or infer cases from linked PRs. If the table is absent, say so and **stop before asking for the site link**.
2. Ask for the URL of the site to test if it has not already been supplied. Test every actionable row in the table, regardless of existing result-cell contents. Preserve the case wording and order. Skip structural headings (for example rows with `-` in all three result columns); do not invent additional test cases.
3. Load the `agent-browser` skill, then run `agent-browser skills get core` before any browser interaction. Follow its installed-version instructions and use the CLI to interact with and observe the site. Do not install packages or switch to another browser-automation tool. Establish what each case should show, perform the actions, and verify the observable outcome rather than treating a click or code inspection as proof.
4. If login or setup is needed, pause for the user to sign in or provide non-secret instructions; do not request passwords in chat. If a case is ambiguous, pause and ask what outcome to expect. If a clear case needs unavailable test data or a third-party service, ask once for help; if it remains unavailable, mark it **Blocked** and continue with independent cases. Continue after failures where possible.
5. Routine test-data changes are allowed. Ask before irreversible or externally visible actions such as deletion of existing data, sending messages, or payments. Safely clean up test-only records you created when permitted; never delete pre-existing data as cleanup. Inspect code only when useful: use the current workspace if it clearly belongs to the tested site, otherwise ask for a codebase link. Code may help explain behavior but cannot by itself earn a Pass; a Pass requires observing the behavior on the site. If a case cannot be verified at runtime, mark it Blocked rather than guessing.
6. Report results **only in the conversation** as a Markdown table with `Testcase | Result | Evidence / blocker`. Use **Pass**, **Fail**, or **Blocked** for each actionable row, with a brief observed fact or specific reason. Report any unfinished cases as Blocked. Do not edit the issue, its testing table, or local test-case files, and do not post a GitHub comment.
